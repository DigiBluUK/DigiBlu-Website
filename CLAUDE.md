# DigiBlu Website — Handover

Marketing site for **DigiBlu** (real company, digiblu.com — a UK AI/digital transformation consultancy). **A Next.js 16 App Router site since 9 Sep 2026**, every page prerendered, the Cloudflare Workers runtime configured through OpenNext; content is markdown; the stylesheet and the interaction code are the original hand-built site's, carried across verbatim. The old single-file site was retired from the tree on 10 Sep 2026 (see Files).

## Branches and releases

**Two long-lived branches since 9 Sep 2026: `dev` is UAT, `main` is production.** Work happens on `dev` (commit and push to `origin dev`); the claude.ai artifact is rebuilt and republished from whatever is checked out, so it is now the UAT preview of `dev`. `main` is the release that is live and only moves when DigiBlu says release: merge `dev` into `main`, tag the next version, push branch and tag. `v1.0.0` is the site as signed off on 9 Sep 2026, the first tag on `main`. **`v2.0.0` is the Next.js build**, released to `main` the same evening by fast-forwarding `dev` (no pull request: the GitHub CLI is not installed here, and the merge had nothing to resolve). Nothing was deployed by that release - Cloudflare is not connected yet - so `main` is "the release" in the branch sense only until the cut-over runbook runs. **Renaming `main` to `dev` was considered and rejected** (it breaks the default assumptions of GitHub, Cloudflare Pages and CI templates), as was a branch named `dev/uat` (the slash makes `dev` a ref namespace, so no plain `dev` branch could coexist). **`v2.2.0` (10 Sep 2026) is the first release without the old site's files**, cut the same day they were retired because the GitHub Pages site (served from `main`'s root, at the `SITE_ORIGIN` default `https://digibluuk.github.io/DigiBlu-Website`) was still showing the old site and its unfixed values gap to stakeholders; with no `index.html` on `main` and `.nojekyll` present it should return 404 once Pages rebuilds - **and it does, since about 10:15 UTC on 10 Sep 2026, after the `v2.2.1` push**: every old address (`/`, `/index.html`, the case-study and legal pages, `/assets/site.css`) answers 404. ## Consent and analytics (9 Sep 2026)

A consent-management foundation built to be lifted onto other sites: **vanilla-cookieconsent 3.1.0** (MIT, no dependencies, ~8KB, accessible dialogs with focus trap, Escape and ARIA) driven by one configuration file, with Google Consent Mode v2 and a GA4 loader that does nothing until analytics is allowed. UK-facing, so the model is opt-in: nothing optional runs before a choice, and rejecting changes nothing about how the site works.

- **Audit first (what the Next.js site actually does in production)**: no cookies of its own; one item of local storage, `digiblu-theme`, written only when the theme button is used; no third-party requests before 11 Sep 2026, and since then exactly one, Cloudflare's Turnstile script and iframe, loaded only when the contact form's last step opens, strictly necessary, no cookies on our origin (DM Sans is self-hosted; the old `index.html` still pulls it from Google Fonts, which is why the old site is not this audit); no embeds, pixels, iframes or external scripts; one form, the contact form, which stores nothing and does not yet submit; navigation is in-page anchors plus full loads of the standalone pages, so a page view is a page load and there is no client-side routing to count. Cloudflare may add its own cookies once the site is on Workers - check after deploy.
- **Files**: `lib/consent/config.ts` (the only site-specific file: site name, measurement id from `NEXT_PUBLIC_GA_MEASUREMENT_ID`, enabled categories, storage mechanism and key, revision, policy links, the necessary-storage disclosure, page-view mode), `lib/consent/gtag.ts` (Consent Mode defaults as a string for the head, signals mapping, the GA4 loader, `trackPageView`, `trackEvent`), `lib/consent/consent.ts` (the library configured from config; `initConsent`, `openConsentPreferences`, `withdrawConsent`, `getConsentState`, `onConsentChange`), `components/consent/Consent.tsx` (mounts once in the root layout; counts client-route page views only when configured), `components/consent/consent.css` (the library's custom properties mapped to the site's tokens, so both dialogs follow the dark/light toggle), `components/consent/CookieSettingsLink.tsx` (the footer's way back in), `.env.example`.
- **Order of operations**: the first script in `<head>` is `CONSENT_DEFAULT_SCRIPT`: it creates `dataLayer`, a queuing `gtag()`, and sets every Consent Mode signal to denied except `security_storage`. Nothing Google can run before it. On mount the library reads any stored decision; `onConsent`/`onChange` call `applyConsentToGoogle`, which sends `consent update` and, if analytics is allowed, injects `gtag/js` once with `send_page_view: false` and sends one `page_view` itself. Reject means the script is never injected: no cookies, no hits, not even cookieless pings. Withdrawal mid-session sets `window['ga-disable-<id>']` (GA's own kill switch, since a loaded script cannot be unloaded), sends the denied signals, and the library's `autoClear` deletes `_ga*`, `_gid*`, `_gat*`. Re-accepting clears the switch and sends a fresh page view; the script is not injected twice.
- **Page views on a single page**: hash changes never count (`usePathname` does not change on a hash). `pageViews: "page-load"` is the setting for this site; `"client-route"` adds one per next/link navigation for a site that has any, without duplicating the loader's first view.
- **Consent record**: local storage, key `digiblu_consent`, JSON with the accepted categories, the revision, a random consent id and timestamps; 182 days; no cookie is set by the consent system at all. Bump `revision` when categories change and the banner asks again. Clearing the key brings the banner back.
- **Categories**: Necessary (read-only, lists the two local-storage items in the dialog), Analytics (offered only when a measurement id is configured, so a category is never shown empty), Marketing (in config, off; adding a marketing service means enabling it and mapping it to the three ad signals, which `consentSignals` already does).
- **Design**: equal-weight Accept all / Reject optional / Manage preferences, no pre-ticked boxes, no dark patterns; the page stays interactive behind the banner (`disablePageInteraction: false`); bottom-left box on desktop clear of the scroll-to-top disc, full width on a phone; the dialogs take the site's font, radii, brand-sweep primary buttons and theme tokens. **The category blocks in the preferences dialog take a 10px radius of their own (10 Sep 2026)**: the library styles them with the button radius, and with the site's pill buttons (999px) an expanded block went pill-shaped and its overflow-hidden description wrapper clipped the description, the table caption and the first and last table columns at the curved corners (reported with a screenshot); `consent.css` overrides the block, title and description-wrapper radii, and the buttons keep the pill.
- **Verified** (dev server, both viewports): new visitor sees the banner with the default signals already denied and no Google request; Reject stores a necessary-only record and loads nothing; the choice survives reload; Cookie settings reopens the dialog without a reload; allowing analytics injects `gtag/js`, sends granted signals, `config` with `send_page_view: false` and exactly one `page_view`; anchor navigation adds none; reload with analytics allowed loads GA and sends one view; withdrawing flips the kill switch and the signals; re-accepting sends one more view with one script tag; clearing storage brings the banner back; console clean. The gtag request itself cannot be observed here (the pane has no outbound network) - Realtime and Tag Assistant confirm it in production.
- **The real property is connected since 10 Sep 2026**: GA4 property "DigiBlu website", web stream "digiblu.com", measurement id **G-RVNLDVSLJ8**, created by DigiBlu following the step-by-step in the session (account data sharing off except support, GDPR data processing terms accepted, enhanced measurement on with site search and form interactions off, a second administrator added). **The id comes from the environment only - `lib/consent/config.ts` has no fallback any more** (it was the `G-XXXXXXXXXX` placeholder, which would have loaded a bogus tag on any build that forgot the variable): production sets `NEXT_PUBLIC_GA_MEASUREMENT_ID` in Cloudflare's build variables, `.env.local` (gitignored) carries it for local testing, `.env.example` documents it, and `next.config.ts` prints a warning at build time when a production build (not `noindex`) has no id, so the live site cannot ship without analytics unnoticed. **Retested against the real id on the dev server the same day**: fresh visit shows the banner with every signal denied and no Google script; Reject stores necessary only and loads nothing; Accept all injects `gtag/js?id=G-RVNLDVSLJ8`, sends `consent update` with `analytics_storage` granted, `config` with `send_page_view: false` and exactly one `page_view`, and Google's `_ga` and `_ga_RVNLDVSLJ8` cookies appear (so the tag ran, and the cookie table names the real cookie); Reject from Cookie settings flips `ga-disable-G-RVNLDVSLJ8` to true, sends the denied signals and clears both cookies. Those test hits reached the property from localhost, which is what the internal-traffic filter in GA4 Admin is for once DigiBlu's addresses are known.
- **Not done, deliberately**: no marketing pixels, no Google Ads, no server-side tagging.

## Pages over dialogs and the contact API (11 Sep 2026)

## Design system

CSS custom properties on `:root`, redefined under `:root[data-theme="light"]` and `@media (prefers-color-scheme: light)`:

- `--ink-rgb`, `--text` — flip between white-on-black and near-black-on-white. Individual elements override `--ink-rgb`/`--text` locally when they sit on a fixed-color surface regardless of theme (hero, accent cards, blue buttons, the Case Studies background band) — grep `--ink-rgb: 255, 255, 255` to find all of them.
- `--bg`, `--surface`, `--surface-2`, `--field-bg` — theme-aware surface tones.
- `--blue` (`#1d6ef5`) — the accent colour for anything that has to be a single colour: text, links, hover tints, focus rings, the values' hover numeral.
- `--brand-fill` — **the primary fill since 9 Sep 2026**: `linear-gradient(135deg, #1b4fd6 0%, #0a1f6e 52%, #050b28 100%)`, the blue-to-navy-to-near-black sweep the service cards and the open team card carry, promoted on request to the one brand surface site-wide ("so brand colour is in sync and this becomes a primary colour of use"). Every surface that was flat `--blue` uses it: the Get in touch button, the scroll-to-top disc, the case-study stat pills, the reader's selected row and current page button, the team strip's arrows, open slice and mobile + disc, the service dialog's CTA, the contact form's next/submit/done buttons and completed step numbers, and the skip link. Borders that matched the flat blue went transparent so the dark end of the sweep shows no blue rim, and the one hover that swapped in a lighter blue now brightens the gradient with `filter`. Same value in both themes on purpose, like the hero; ink on it is pinned white and clears AA at every size (white on the lightest stop is ~6.5:1). `.blog-art.a2` is the same sweep as a literal, kept separate because the art panels are a set of four.
- `--brand-ink-1/-2/-3` and `--brand-ink` — **the same sweep for accents** (9 Sep 2026, "that colour flows through all the way ... our values when you hover, the header, the geometric icon"): things that sit ON the page rather than under white ink. In light theme the three tokens are the fill's own stops, so accent and surface are literally one colour. **In dark theme they are the family's bright end** (`#6aa4ff`, `#2f7bff`, `#1d6ef5`): the fill's navy end is 1.4:1 on black and even its brand-blue start only 3.1:1, so the fill sweep cannot be text there; the bright sweep measures 6.6, 5.4 and 4.56:1, every stop clear of AA for the 12px label. Consumers: the "Our values" label (gradient text, `width: max-content` so the sweep crosses the words), the values' hover and focus numeral (gradient text, applied in the hover state only because the phone column's collapsed numerals are translucent and a permanent gradient would bleed through, and transitioned on the way in only or the numeral flashes out) and hairline (`border-image`), the client quote's left rule, the contact form's success tick (its own `#tickBrand` gradient) and **the About mark** - the 78 mark dots are emitted a second time by `dots.cjs` in a `<g class="mk-lit">` filled from `#geoBrand`, whose opacity is the `--mark-lit` the geo IIFE already writes; the ink dots underneath stay `--text`. Colour tokens rather than a gradient alone so SVG `<stop>`s can read them (`.gb1/.gb2/.gb3`). What stays flat `--blue`: focus rings, the checkbox `accent-color` and the quote rule's fallback colour under its border-image - indicators and fallbacks, not accents.
- `--section-y` (72px desktop / 56px ≤900px), `--head-gap` (48px / 36px) — **the vertical rhythm.** Every section pads from `--section-y`; every heading's trailing margin is `--head-gap`. Boundary gap between any two adjacent sections should measure `2 × --section-y`. If you add or restructure a section, give it `padding: var(--section-y) var(--gutter)` directly — don't hand-roll a padding value, and don't put that padding on an inner wrapper only (this exact mistake broke the rhythm twice this session, see Case Studies below).
- `--maxw` (1500px), `--gutter` (24px) — content width and page margin.
- `--page-ink-rgb` / `--page-text` — **escape hatch, never overridden below `:root`.** `.hero` and `.cases` pin their own white ink so text stays legible on their artwork. Anything nested inside them that is visually part of the *page* rather than that surface must opt back out via `var(--page-ink-rgb)`, or it inherits white ink while taking a theme-aware background. That exact mismatch made the mobile menu render white-on-white (contrast 1.0, completely unreadable) in light mode on every viewport ≤900px. `.mobile-menu` is the current consumer.
- `--ink-a-faint` / `-low` / `-mid` / `-high` / `-aa` — alpha steps for de-emphasised text, **higher in light mode**. The dark values (0.40/0.45/0.50/0.55/0.58) are the originals and are unchanged; the light overrides (0.60/0.62/0.64/0.66/0.66) exist because the same alpha on white measured only 2.6–4.3:1. Use these tokens rather than a literal `rgba(var(--ink-rgb), 0.5)` for any muted text, or it will fail AA in light mode. Anything already at 0.6+ clears 4.5:1 in both themes and is left literal.
- `color-scheme` is declared on `:root` in all three theme states (dark default, explicit light, OS-preference light). It is what tells the browser which way round to paint its own native UI - without it the UA assumes a light page and paints a pale scrollbar over the dark site, and it is the only thing keeping the native bar in the right key in browsers that ignore the custom scrollbar rules.
- **Scrollbars are styled site-wide**, not per-container: a `*::-webkit-scrollbar` rule plus `scrollbar-width`/`-color` on `html` for Firefox, all resolved through `--ink-rgb` so both themes need one rule. `border: 3px solid transparent` + `background-clip: content-box` is what insets the thumb inside its 10px gutter. The universal selector is deliberate so containers added later are covered; `::-webkit-scrollbar` does not inherit the way `scrollbar-color` does, so it cannot just be set on `html`. Confirm it applied by measuring the rendered gutter (`innerWidth - documentElement.clientWidth` = 10, against a 15-17px Windows default), not by reading the rule back.
- Theme toggle button (`#themeToggle`) persists an explicit choice to `localStorage['digiblu-theme']`; absent a stored choice, `prefers-color-scheme` decides. A small inline `<script>` in `<head>` (and re-emitted before `<body>` in the artifact build) stamps `data-theme` before first paint to avoid a flash.

**The About figure** (`.geo-figure`) is a **dot lattice** in which the DigiBlu **db is rendered by dot size alone** - a halftone. Generated by `scratchpad/geo/dots.cjs`. 900 circles on one exact 30x30 pitch; 78 of them carry the mark, **and those 78 are emitted a second time** (since 9 Sep 2026) in a `<g class="mk-lit">` filled with the brand sweep - see `--brand-ink` in the Design system - so the cursor script sees 978 circles, the copies sharing the ink dots' classes so they pulse and part in step.

- **Why it is dots and no longer dashes.** The dash version carried the mark in each dash's ANGLE, turning to follow the local contour of a letterform. That is inherently ragged - the strokes are curved, the grid is not, and a curve approximated by grid-aligned ticks reads as noise well before it reads as a letter. It was reported as "messy" and no amount of blur or threshold tuning would have fixed it: the representation was wrong, not the parameters. On a lattice where every dot is the same shape on the same pitch and **only the radius varies**, there is no angle for anything to disagree about, so it cannot look untidy. Keep that property in mind before adding any per-dot rotation or jitter.
- **Radius comes from supersampled coverage, not a point sample.** Each cell asks what fraction of its own area the letterform covers, so an edge dot is genuinely part-sized rather than snapping between full and nothing. That is what keeps the outline smooth at this pitch; a single sample per cell produces a visibly stepped edge. **Only mark dots take that radius** (8 Sep 2026): coverage used to size every dot, so 54 dots with up to half coverage sat around the outline and inside the counters, enlarged but still in the field's faint ink - grey blobs beside the blue mark, reported as a glitch. A dot that does not make the mark now stays at the field radius; the mark's own dots keep their coverage-graded sizes, so the edge stays smooth.
- **The mark pulses less than the field** (`geo-pulse-mark` at 0.95-1.06 against `geo-pulse` at 0.82-1.14) and sits at full ink against the field's 0.34. At the field's amplitude the mark's edge visibly crawls.

## SEO

**`SITE_ORIGIN` drives every canonical, `og:image`, JSON-LD self-URL, sitemap entry and `robots.txt` line, and it is environment-overridable** - see "Serving from a different origin" above, and "Branches and releases" for which branch is live. **Per-engagement share cards**: each case study has its own 1200x630 card (`assets/og/case-studies/<key>.jpg`); blog and legal pages fall back to the site-wide `og-image.jpg`. `pageHead()` takes optional `ogImage`/`ogImageAlt`, and the alt text follows the image so a card naming one case study is never announced on another page.

An SEO audit was run and its findings prioritised into a to-do list before any of it was actioned (the user explicitly asked for research first, action second). Two items have been done; the rest are tracked in Known follow-ups below.

- **Biggest lever, deliberately not touched: the single-URL architecture.** Every blog post, case study, and legal page only exists as a JS-populated modal, not a separate crawlable URL, and the content only renders into the DOM on click rather than being present on load — both cap how well any of it can be individually indexed or ranked. Fixing this properly means giving each piece its own pre-rendered page, which cuts against this project's "no build tooling, no framework" identity (see the top of this file) — a real architectural decision, not a quick edit, so it's flagged rather than done unilaterally.
- **`Organization` JSON-LD**  (`<head>`). The `FAQPage` block was removed with the FAQ section - leaving schema describing content no longer on the page would have been invalid structured data. The `@graph` wrapper was flattened to the single remaining node. `Organization` carries name, legal name, URL, `logo`, `image`, description, the real registered address (`PostalAddress`, matching the footer's `CM1 1NH` — the Terms of Use said `CM1 2NH` until 10 Sep 2026, when the Terms read-through checked Companies House and corrected it to the registered office's CM1 1NH), and `sameAs` → the LinkedIn page.png` and `assets/og-image.jpg` are both `<head>`-only, so they have zero effect on the published artifact.** The rebuild script strips `<head>` entirely (Artifacts supply their own), so nothing in this SEO pass is visible on the claude.ai preview — it only matters once/if this ships to the real `digiblu.com`. Don't be surprised the artifact looks unchanged after this work; that's expected, not a bug.
  - Both images were generated via canvas in the browser preview, then decoded straight from the raw tool-result payload with Node (`Buffer.from(base64, 'base64')`) rather than hand-relayed through a written response — for `og-image.jpg` specifically, the base64 payload was long enough to overflow into a saved tool-result file, which turned out to be the safer path anyway (byte-exact, no transcription risk). Verify any future asset generated this way by checking the file's real signature and pixel dimensions (PNG: bytes 16–23 big-endian; JPEG: walk `0xFFC0`–`0xFFC3` SOF markers) before trusting it — don't assume a `toDataURL()` round-trip succeeded just because the tool call didn't error.
- **`og:image`/`twitter:image` now point at a purpose-built 1200×630 card** instead of reusing `hero.jpg` at whatever crop the browser happened to produce. Built from the real hero art (cover-cropped to the OG aspect ratio, not a new background), the same left-to-right scrim gradient the live `.hero` section uses, and the real DM Sans font loaded via `FontFace` before drawing — not a generic canvas fallback font. Added `og:image:width`/`height`/`type` and the previously-missing `twitter:title`/`description`/`image` (only `twitter:card` existed before).

## Environment note

Browser-preview screenshot tooling has been unreliable across sessions (`the page is not compositing frames` / stuck mid-CSS-transition reads / hangs on `img.decode()` for lazy images while the pane is hidden).

**Read this before trusting a `getComputedStyle` result on any animated property.** Because the pane often isn't compositing, `requestAnimationFrame` never fires, so **CSS transitions freeze at t=0 and never advance**. `getComputedStyle` then returns the *start* of the transition, not the target — which reads exactly like a broken style rule. This cost real debugging time twice (the G-Cloud `filter` invert and the blog filter pill background both looked broken and were not). When checking a property that has a `transition` on it, set `el.style.transition = 'none'` and force a reflow first, then read. Waiting with `setTimeout` does **not** help — a frozen transition never completes. `file://` navigation also renders as a non-interactive static snapshot in this tool — use the `.claude/launch.json` dev-server config (`npx http-server` on port 4173) instead, so the Browser preview tool loads over real `http://`. Verification has leaned on `getComputedStyle`, `getBoundingClientRect`, canvas pixel-sampling for contrast, direct `fetch()`/network checks for asset loading, `querySelector`/`click()` simulation for interactive flows, and direct cascade/rule inspection instead of visual screenshots. If screenshot tooling is healthy in a future session, a straightforward visual pass is still worth doing — everything here was checked numerically, not eyeballed.
