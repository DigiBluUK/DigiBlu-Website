# DigiBlu Website — Handover

Marketing site for **DigiBlu** (real company, digiblu.com — a UK AI/digital transformation consultancy). Single-file HTML/CSS/JS, no build tooling, no framework. Published as a claude.ai Artifact for sharing.

## Deploying to a real host (Netlify etc.)

**Deploy `index.html` and the folders — NOT `digiblu-site.html`.** This tripped up a real deploy already, so it is worth being blunt about:

| File | What it is | Deploy it? |
|---|---|---|
| `index.html` | The actual website. Full `<head>` (title, meta, canonical, OG/Twitter, favicon, JSON-LD), links `assets/site.css`. | **Yes — this is the site.** |
| `digiblu-site.html` | The **claude.ai Artifact build only**. `<head>` deliberately stripped (Artifacts supply their own) and every asset base64-inlined into one 936KB file. It literally begins `<style>` — no `<!DOCTYPE>`, no `<html>`, no `<head>`, no `<title>`, no favicon, no JSON-LD, no OG tags. | **No.** Deploying it loses the tab title, favicon, social preview and all SEO structured data. |

Upload **the whole project folder**, which must contain:

```
index.html   assets/   case-studies/   blog/   legal/   sitemap.xml   robots.txt
```

Netlify serves `index.html` at `/` automatically, and the 20 static pages resolve at `/case-studies/<key>.html`, `/blog/<key>.html`, `/legal/<slug>.html`.

**If a deploy shows an old version:** first check you didn't upload `digiblu-site.html` (or, historically, the stale `digiblu-artifact.html` — deleted 5 Aug 2026, it was a 31 July build with no Clients section, no Blog, no real case studies and no hero animation, and was the most likely culprit). Then hard-refresh (Ctrl/Cmd+Shift+R) — a normal reload will happily serve a cached `index.html`.

**One deployment-time caveat:** `sitemap.xml` and `robots.txt` hardcode `https://digiblu.com/...`. On a `*.netlify.app` preview URL those point crawlers at the real domain instead of the preview. Harmless for a private preview; change `SITE_ORIGIN` at the top of `generate-static-pages.js` and re-run if you ever want them to match a different domain.

## Serving from a different origin

`SITE_ORIGIN` drives every canonical, `og:image`, JSON-LD self-URL, sitemap
entry and `robots.txt` line. It defaults to `https://digiblu.com` and is
**overridable from the environment**, so a staging host or preview deployment
does not need the value forked in the source:

```bash
node generate-static-pages.js                                  # digiblu.com
SITE_ORIGIN=https://staging.example.com node generate-static-pages.js
```

Point it at a host that is not actually serving the files and crawlers are
told a site you do not control is the canonical one, and no social share card
resolves. Note a GitHub Pages *project* site is served under a `/<repo>`
subpath, so the repo name is part of the origin - omit it and every generated
URL 404s.

**The stylesheet cache buster is generated, not hand-typed.** `?v=` on the `site.css` link is a 10-char hash of the stylesheet's own bytes, stamped into `index.html` and every generated page by `generate-static-pages.js`. It was a hand-typed date until 2 Sep 2026, when it failed exactly as hand-maintained values do: the stylesheet changed in six commits after the last bump, so returning visitors got fresh HTML against a stale cached stylesheet. The newly renamed client-logo classes matched no rules at all and **ten of the fourteen logos rendered as nothing**, which reads as a broken carousel rather than an old page. Never hand-edit the value - run the generator, which is idempotent and a no-op when already correct.

**The origin lives in two places and the generator syncs both.** The static
pages are generated, but `index.html`'s own canonical/OG/JSON-LD URLs are
hand-authored - which is how the homepage once ended up claiming a different
canonical host from its own static pages. The generator now rewrites that
`<head>` too, reading the current value from the canonical tag so it
self-corrects whatever state the file is in, and is a no-op when already
correct. It is scoped to `<head>` deliberately: the ~15 www.digiblu.com links
in the body are provenance records for where the blog and legal copy was
sourced and must keep pointing at DigiBlu on every host.

### Rebuild procedure

`digiblu-site.html` is `index.html` with:
1. `<head>` stripped (Artifacts supply their own) — this also means `assets/logo.png`, `assets/og-image.jpg` and the JSON-LD block (all `<head>`-only, added for SEO) never reach the artifact build at all; see the Files table.
2. CSS read from `assets/site.css` (extracted out of `index.html` into its own file, linked via `<link rel="stylesheet">` — see below) rather than sliced out of an inline `<style>` block. `index.html` no longer contains a `<style>` tag at all.
3. The Google Fonts `<link>` replaced by an inlined `@font-face` (`assets/dmsans.woff2` → base64)
4. `url('assets/hero.jpg')` and `url('assets/footer-bg.jpg')` replaced with `data:image/jpeg;base64,...` inside the CSS
5. Each `img: 'assets/badges/*.png'` (a JS string literal inside `BADGE_DETAILS`, in the `<script>` block — which is part of `$body`, not `$css`) replaced with `img: 'data:image/png;base64,...'`. These are the badge popup's original full-colour images; each of the 6 files appears exactly once (one `BADGE_DETAILS` entry per badge), so no de-dupe concerns like the historical `<img src>` version below.
7. Each `'assets/case-studies/<key>.jpg'` literal in the `CASE_PHOTO` map (in the `<script>` block, so `$body`) replaced with a `data:image/jpeg;base64,...` literal. **This step was missing from the documented script until the 2 Sep 2026 code review** - the working loop existed only in a session scratchpad, so anyone rebuilding from this page would have shipped an artifact whose eight case-study photos all 404ed. The loop throws on a missing path for exactly that reason.
6. `url('assets/clients/*.png')` and `url('assets/badges/mask/*.png')` replaced with `data:image/png;base64,...`. These live in **CSS** (`mask-image`), not the body, so they go through the `$css` replace loop rather than the `$body` one. Each file appears twice (`-webkit-mask-image` + `mask-image`), so expect **22 substitutions across 11 files**.

**Note:** step 5 used to inline `<img src="assets/badges/*.png">` tags in the marquee itself — historical, since the marquee switched to CSS masks (cut the build from 925KB to 617KB, because a CSS `url()` is written once and shared across every selector, whereas each `<img>` carried its own copy of the base64 payload). The badge originals came back into `$body` for a different reason (the popup's `img:` field, described above), so this step still exists but now targets a JS string literal, not an `<img src>` attribute.

**Why the CSS extraction happened:** once static pages for case studies/blog/legal existed (see the Static pages section below), 21 pages needed the site's ~68KB of CSS. Duplicating it into every generated page would have meant 21 copies to keep in sync by hand forever; extracting it once to `assets/site.css` and having every page (`index.html` and all 20 generated pages) `<link>` to it keeps a single source of truth. The artifact build's actual output is unaffected — the CSS ends up inlined into `digiblu-site.html`'s `<style>` block exactly as before, just read from a file instead of sliced out of inline markup.

**Real bug the extraction introduced and fixed the same session:** the CSS's `url('assets/hero.jpg')`, `url('assets/footer-bg.jpg')`, `url('assets/badges/mask/*.png')` and `url('assets/clients/*.png')` references were all written when this CSS lived *inline in `index.html`*, at the project root — so `assets/hero.jpg` correctly meant "go into the `assets/` folder from here." Once that same CSS became `assets/site.css`, a file that itself *lives inside* `assets/`, those same relative paths now resolve from `assets/` — turning `url('assets/hero.jpg')` into a request for `assets/assets/hero.jpg`, which doesn't exist. Every background image and mask on both `index.html` and every generated static page 404'd until this was caught (via `read_network_requests` — `getComputedStyle().backgroundImage` alone doesn't catch this, since it returns the `url(...)` string regardless of whether that URL actually resolves to a real file). Fixed by stripping the redundant `assets/` prefix inside `assets/site.css` itself (`url('assets/hero.jpg')` → `url('hero.jpg')`, all 24 occurrences), which also meant updating the rebuild script's `$css.Replace(...)` search strings to match the shorter paths. **The lesson: CSS `url()` values are always relative to the stylesheet file's own location, never to the HTML page that links it in** — remember this before moving any CSS file, or adding a new `url()` reference to `assets/site.css` in the future (new references should be relative to `assets/`, e.g. `url('new-image.png')`, not `url('assets/new-image.png')`).

**Always verify before publishing**: no `fonts.googleapis` / `assets/` strings left in the output (confirms everything inlined), section count matches, no dead `href="#"` links introduced.

**Verify with a regex that can actually fail.** A check like `/\.tp-\w+ \{ background-image: url\(data:/` reported 2 of 8 team photos inlined and looked like a real bug; the replacements were all fine and the pattern was simply too strict about whitespace. Prefer asserting the *absence* of unresolved references (``html.match(/url\('(?:assets\/|team\/|clients\/|badges\/)[^']*'\)/g)`` → `[]`) over counting successful ones, since the negative form can't be fooled by formatting.

## Static pages

**Why this exists:** on request, walked through the SEO to-do list's biggest item — every case study, blog post and legal doc only ever existed inside a JS-populated modal on the single-page site, with no separate URL, and the content only rendered into the DOM on click rather than being present on load. Both cap how well any of it can be individually indexed. The options discussed: leave it (zero effort, permanent ceiling), adopt a real static-site framework (the "proper" fix, but works against this project's deliberate "no build tooling, no framework" identity), or a bespoke no-framework generator reusing content already authored in `index.html`. Went with the third — `generate-static-pages.js` (see Files table).

- **13 real pages**: 8 case studies (`case-studies/<key>.html`), 5 legal docs (`legal/<slug>.html` — using the real digiblu.com URL slugs already stored in `LEGAL_DETAILS[key].url`, e.g. `privacy-policy`, not the terser internal keys like `privacy`). Each has its own unique `<title>`/`meta description`/canonical/OG tags and a JSON-LD block (`WebPage` for case studies and legal docs) — verified to parse and, for the FAQ block on the homepage, to match the visible page text exactly, since Google requires the schema to mirror what's actually shown.
- **The homepage's modal experience is completely unchanged.** These pages are additional, not a replacement — a normal visitor clicking a case study card still gets the same quick-view popup they always did.
- **Real internal links, not just a sitemap entry.** Case study cards (all 3 featured + every row in the reader sidebar), blog cards, and the footer's Legal links are now real `<a href="case-studies/<key>.html">` etc. (converted from `<button>`/JS-created buttons) with a click handler that checks for modifier keys (`e.metaKey || e.ctrlKey || e.shiftKey || e.altKey || e.button === 1`) before doing anything — a plain left-click still `preventDefault()`s and opens the existing quick-view modal exactly as before; ctrl/cmd/middle-click, right-click "open in new tab", or a crawler following the link all get the real static page. Without this, the 20 pages would be **orphan pages** — nothing on the homepage actually points to them except the sitemap, which is a much weaker discovery signal than a real internal link. Converting `.case-index-item` (JS-created in `renderIndex()`) from `document.createElement('button')` to `createElement('a')` needed one small CSS addition (`text-decoration: none; color: inherit;` on `.case-index-item`) since anchors get a default underline/link-colour that buttons never did — the kind of regression that's easy to miss since it's purely cosmetic and every other property still worked.
- **The footer's Legal links now point at the real generated pages** (`../legal/privacy-policy.html` etc.) rather than only opening `#legalModal` — same progressive-enhancement pattern as above (plain click still opens the modal), so the modal isn't dead code, but a crawler or ctrl-click gets the genuine page.
- **CSS extraction was the prerequisite**, not an afterthought: see the CSS `url()` note above the rebuild script — `assets/site.css` is shared by `index.html` and all 20 generated pages via `<link rel="stylesheet">`, one `../assets/site.css` reference for pages one directory down.
- **The nav needed a real fix, not just reuse, once it left the hero.** `.logo`, `.theme-toggle` and `.nav-toggle` hardcode `color: #fff` in the homepage CSS, because on the homepage the nav always sits on `.hero`'s dark photo background regardless of theme. These standalone pages have no hero behind their nav — on a plain (correctly theme-aware) page background, that hardcoded white would be illegible in light theme, the same bug category as the mobile-menu's documented white-on-white fix, but a different mechanism: those three rules set a literal colour rather than reading `--ink-rgb`, so redefining a variable on a wrapper doesn't reach them. Fixed with `.page-header .logo, .page-header .theme-toggle, .page-header .nav-toggle { color: var(--text); }` (`assets/site.css`) and the generator's `<nav class="page-header">` (vs. the homepage's bare `<nav>`). Verified explicitly in both themes — dark theme was already correct by coincidence (the default `--text` happens to be white), so testing only dark theme would have missed this.
- **Body content is rendered directly**, not copied from the modal's `innerHTML` at build time — the generator has its own `renderCaseStudy`/`renderBlogPost`/`renderLegalDoc` functions producing the same markup shape (`.case-modal-eyebrow`, `.case-stats`/`.case-stat`, `.case-section`, `.case-modal-quote`, `.service-modal-list`/`.service-modal-item`, `.blog-full-text`) directly from the data objects, wrapped in a new `.detail-page` container (`max-width: 760px` — matching the modals' own reading widths — `padding: var(--section-y) var(--gutter)`, the project's standard section-rhythm pattern) instead of a `.modal-panel`. Blog pages render the **full** article directly (no summary-first toggle — there's no space constraint on a real page the way there is in a popup).
- **Verification**: every page's `<title>`/meta/JSON-LD checked (fetch + parse, not just visual spot-checks); CSS confirmed to actually load real image bytes (`getComputedStyle().backgroundImage` including a `url(...)` string is not sufficient — see the CSS `url()` gotcha above, which was caught exactly this way); the permalink progressive-enhancement checked both directions — `dispatchEvent(new MouseEvent('click', {cancelable:true}))` then reading `event.defaultPrevented` for the plain-click path (confirms the modal opens and navigation is blocked) and `{ctrlKey: true}` for the modifier path (confirms `defaultPrevented` stays `false`, i.e. a real ctrl-click would navigate). **Avoid calling `.click()` directly on these anchors from a verification script** — unlike `dispatchEvent`, it can trigger real navigation before the script can read the result, tearing down the page mid-script (hit this while testing; switching to `dispatchEvent` + reading `defaultPrevented` synchronously fixed it).
- **The page title is an `<h1>`, and needs its own CSS rule.** Two defects found on the finalisation review and fixed together: every generated page shipped with **no `<h1>` at all** (the title was an `<h2>`, carried over from the modal markup it was modelled on) — a real miss on pages that exist specifically to be indexed — and that heading was rendering at **browser-default styling** (24px, `line-height: normal`, no bottom margin), because every heading rule in `assets/site.css` is scoped to a specific section (`.blog h2`, `.cases h2`, `.case-modal-body h2`, …) and **none of them match inside `.detail-page`**. Fixed by emitting `<h1>` and adding a `.detail-page h1` rule (`clamp(26px, 3.4vw, 34px)`, a step above the modal's 26px since it's a page title). Worth remembering the general trap: this site has **no global `h1`/`h2` typography** — a heading in a new container inherits nothing and silently falls back to UA styles, which looks plausible enough to miss unless you actually read the computed `font-size`.
- **"Get in touch" / "Contact Us" deep-link into the contact modal.** That dialog only exists on the homepage, so these link to `../index.html#contact`, and `index.html` has a small `openFromHash()` in the contact-modal IIFE that opens it when the hash is `#contact` (on load, plus a `hashchange` listener for the already-on-page case). Previously they dumped the visitor on the homepage with no way to reach the form. The back-link at the top of each page reads **"Back to home"**, not the original "Back to digiblu.com" — nonsensical wording once these pages *are* digiblu.com.
- **Known limitation, not yet done**: `robots.txt`/`sitemap.xml` are generated but only meaningful once deployed to a real domain; deploying should use `index.html` + the lightweight asset files directly, not the base64-inlined artifact build (see Known follow-ups).

## Design system

CSS custom properties on `:root`, redefined under `:root[data-theme="light"]` and `@media (prefers-color-scheme: light)`:

- `--ink-rgb`, `--text` — flip between white-on-black and near-black-on-white. Individual elements override `--ink-rgb`/`--text` locally when they sit on a fixed-color surface regardless of theme (hero, accent cards, blue buttons, the Case Studies background band) — grep `--ink-rgb: 255, 255, 255` to find all of them.
- `--bg`, `--surface`, `--surface-2`, `--field-bg` — theme-aware surface tones.
- `--blue` (`#1d6ef5`) — the single accent color, used everywhere (buttons, links, active states, gradients).
- `--section-y` (72px desktop / 56px ≤900px), `--head-gap` (48px / 36px) — **the vertical rhythm.** Every section pads from `--section-y`; every heading's trailing margin is `--head-gap`. Boundary gap between any two adjacent sections should measure `2 × --section-y`. If you add or restructure a section, give it `padding: var(--section-y) var(--gutter)` directly — don't hand-roll a padding value, and don't put that padding on an inner wrapper only (this exact mistake broke the rhythm twice this session, see Case Studies below).
- `--maxw` (1500px), `--gutter` (24px) — content width and page margin.
- `--page-ink-rgb` / `--page-text` — **escape hatch, never overridden below `:root`.** `.hero` and `.cases` pin their own white ink so text stays legible on their artwork. Anything nested inside them that is visually part of the *page* rather than that surface must opt back out via `var(--page-ink-rgb)`, or it inherits white ink while taking a theme-aware background. That exact mismatch made the mobile menu render white-on-white (contrast 1.0, completely unreadable) in light mode on every viewport ≤900px. `.mobile-menu` is the current consumer.
- `--ink-a-faint` / `-low` / `-mid` / `-high` / `-aa` — alpha steps for de-emphasised text, **higher in light mode**. The dark values (0.40/0.45/0.50/0.55/0.58) are the originals and are unchanged; the light overrides (0.60/0.62/0.64/0.66/0.66) exist because the same alpha on white measured only 2.6–4.3:1. Use these tokens rather than a literal `rgba(var(--ink-rgb), 0.5)` for any muted text, or it will fail AA in light mode. Anything already at 0.6+ clears 4.5:1 in both themes and is left literal.
- `color-scheme` is declared on `:root` in all three theme states (dark default, explicit light, OS-preference light). It is what tells the browser which way round to paint its own native UI - without it the UA assumes a light page and paints a pale scrollbar over the dark site, and it is the only thing keeping the native bar in the right key in browsers that ignore the custom scrollbar rules.
- **Scrollbars are styled site-wide**, not per-container: a `*::-webkit-scrollbar` rule plus `scrollbar-width`/`-color` on `html` for Firefox, all resolved through `--ink-rgb` so both themes need one rule. `border: 3px solid transparent` + `background-clip: content-box` is what insets the thumb inside its 10px gutter. The universal selector is deliberate so containers added later are covered; `::-webkit-scrollbar` does not inherit the way `scrollbar-color` does, so it cannot just be set on `html`. Confirm it applied by measuring the rendered gutter (`innerWidth - documentElement.clientWidth` = 10, against a 15-17px Windows default), not by reading the rule back.
- Theme toggle button (`#themeToggle`) persists an explicit choice to `localStorage['digiblu-theme']`; absent a stored choice, `prefers-color-scheme` decides. A small inline `<script>` in `<head>` (and re-emitted before `<body>` in the artifact build) stamps `data-theme` before first paint to avoid a flash.

## Page structure (top to bottom)

1. **Hero** — full-bleed `assets/hero.jpg`, nav (desktop links + hamburger below 900px), theme toggle, headline, CTA opens the contact modal. The small "DigiBlu" eyebrow above the headline was removed on request, and the nav wordmark is now the real logo image (`.logo-mark`, see the Files table).
   - **`.hero-logo` sits above the headline at every width.** It was mobile-only at first (the nav carries the same lockup on desktop), then brought back everywhere on request. A separate class from `.logo-mark` on purpose: that one is cropped to icon-only below 900px for the nav bar. Sized on the mask's exact 4.1184 aspect - the mask has zero transparent padding (verified by decoding its alpha), so the box IS the visible mark and any drift letterboxes it. Desktop 148.3x36, mobile 115.3x28. The bottom margin is a *box* gap, not the optical one: the h1's cap-top sits ~6.8px below its line box, so 15px renders as ~22px of real whitespace. `background-color` must stay `var(--text)`, **not** `currentColor` - `.hero` pins white ink for its children, but `color` is computed on body from the root's `--text` and merely inherits, so `currentColor` resolved to near-black and the mark vanished on the hero art in light theme.
   - **The nav is fixed and frosted.** `.site-nav` is a full-width `position: fixed` positioner; `nav` inside it is the max-width content row. At rest it is fully transparent over the hero photo; past 24px of scroll a `.scrolled` class turns `nav` into an **inset, rounded glass panel** — `rgba(var(--glass-rgb), 0.68)` + `backdrop-filter: blur(12px)` (was `blur(18px) saturate(160%)` until the 2 Sep 2026 scroll-smoothness pass: backdrop-filter cost scales with area x radius^2 and runs during *all* scrolling, so it was the heaviest single effect for a weak GPU at high DPI - a Surface Pro X stuttered; 12px without the saturate looks near-identical at roughly half the cost), inset `--gutter` from each edge with a 12px top margin — so page content is visibly moving beneath it. The glass lives on `nav`, not `.site-nav`, which is what keeps it wrapping the nav options rather than painting edge to edge (it was a solid full-width bar first; that read as "a wide white background" and was changed on request).
   - **0.68 opacity is a floor, not a taste call.** The panel floats over arbitrary content, so its text contrast cannot be computed statically the way a flat surface's can; that opacity keeps labels legible even over a dark image scrolling underneath. There is an `@supports not` fallback to a near-opaque surface where `backdrop-filter` is unavailable.
   - **`.scrolled` must re-point `--ink-rgb`/`--text` at `--page-ink-rgb`/`--page-text`.** `.site-nav` is a DOM descendant of `.hero`, which pins white ink for everything inside it regardless of scroll position, so a plain `var(--text)` here would still resolve to hero-white and be invisible on light-theme glass. `.logo`/`.theme-toggle`/`.nav-toggle` additionally hardcode `#fff` (for the transparent over-photo state), so they need their own explicit override — redefining the variable does not reach them.
   - **`--nav-h` is measured from the live nav by script, not hardcoded**, and drives both `.hero`'s `padding-top` (the nav is out of flow now, so the headline would otherwise ride up) and `html { scroll-padding-top }` (`+26px` to clear the glass panel's top margin). That scroll-padding is what fixed the "lots of white space above the section when the page settles" report.
   - **`.hero-spark`** — small lights travel back and forth along the bright diagonal bands baked into `hero.jpg`, on request ("a star like light going around the lines of the blue arrows"). Paths are not eyeballed: `hero.jpg` was drawn to a canvas and each bright ridge traced by sampling actual pixel brightness (`(r+g)/2` — the highlight edges are near-white so R and G both spike, while the deep-blue fill stays low on both) with a perpendicular-recentring ridge-follower. The SVG overlay uses `viewBox="0 0 1672 941"` (hero.jpg's native size) with `preserveAspectRatio="xMidYMid slice"`, which reproduces the background's `center / cover` crop math exactly — every path stays pixel-aligned with the artwork at every viewport size, including the heavy crop on narrow/tall phone viewports (where much of a path simply scrolls out of the visible slice, same as the art itself). Motion is plain SVG SMIL (`<animateMotion>`, `keyPoints="0;1;0"` for a smooth there-and-back with no end-of-cycle jump) on pairs of `<circle>`s (a soft radial-gradient glow + a small bright core) — no JS animation loop, no per-frame `<feGaussianBlur>` filter (the glow comes from the gradient definition, not a runtime filter), so it's compositor-cheap. `.hero-spark` is `position:absolute; z-index:0; pointer-events:none`, placed as the first child of `.hero` so it paints behind the flex-item nav/headline/CTA (verified via `elementFromPoint` click-through checks, not assumed); hidden under `prefers-reduced-motion: reduce`.
     - **Three lights, not one**, on request ("not just one line of movement, it's happening on the other lines too but maybe one or two at a time") — three separate bands traced the same way, each with its own `<g>` wrapping its glow+core circle pair. Position (`<animateMotion>`, 12s ping-pong per light, `begin` staggered by a few seconds per light so they don't move in lockstep) is independent from **visibility**, which is gated by a separate `<animate attributeName="opacity">` per `<g>` on a longer, shared 24s envelope (`values="0;1;1;0;0"` — fade in, hold, fade out, stay off) with each light's envelope offset by 8s (`begin="0s"/"8s"/"16s"`). The three 24s windows overlap by design, so at any moment roughly 1-2 lights are visible, never all 3 — verified by seeking `setCurrentTime()` across a full 24s cycle at 1s steps and counting how many `<g>`s had `opacity > 0.5` at each sample: 0 lights only at the single t=0 boundary instant, 1 light for 14 of 25 samples, 2 lights for 10, **never 3**.
     - **Verifying this needed a different technique than the rest of the site.** The preview pane reports `document.visibilityState === 'hidden'` here, which throttles real-time SMIL/CSS timing to a full stop (`svg.getCurrentTime()` stays at `0` indefinitely) even though the element isn't actually broken — a stricter version of the frozen-transition issue in the Environment Note below. Confirmed the wiring is correct instead by seeking the clock directly with `svg.setCurrentTime(t)` at several `t` values and reading `getBoundingClientRect()`/`getComputedStyle().opacity` after each seek: the original single light's positions traced a clean symmetric round trip (t=3 and t=9 landed on the same point, as did t=1.5/t=10.5 and t=0/t=12), and the three-light opacity envelopes showed exactly the staggered 1-2-visible pattern described above — neither can be demonstrated by real-time playback in this environment, but a direct seek can.

This replaced a badge-image marquee on request ("change from badges to written, easier to read"), and the badge *masks* under `assets/badges/mask/` are consequently no longer referenced by anything — only the full-colour originals survive, for the popup.

They are the only visible label on a real button, and at that weight they measured 1.8:1 - decoration, not a control. The *whole composition* sticks, not the list alone: heading, narrative, figure and values together, so the hold reads as the page pausing on About rather than a bare list floating in an empty screen. Nothing is hijacked - no `preventDefault`, no scroll listener moving the page - so a flick, a scrollbar drag and PageDown all behave normally and the user is never actually stuck.

The true section gap at release is the standard 2 x --section-y; the space was the pin's runway. Centred (`top: max(nav + 18px, (100vh - --about-inner-h) / 2)`, height written by the pin IIFE before it reads the top), the spare splits above and below and reads as a held slide. The hold was also cut from 130vh to 85vh for the same reason.

A sticky element taller than the viewport pins its top and puts its own bottom permanently out of reach; the composition measures ~734px, so a short screen drops the pin entirely and falls back to the unpinned mapping below. Also dropped under `prefers-reduced-motion`, where the values are all revealed at once and the hold would be 130vh of nothing happening.

The remaining fill now rides the pin's progress and completes by 18% of it, so the sentence finishes just as 02 opens. Anything else keyed to this block travelling will break the same way.
     - **Both handlers share one `window.__aboutPinProgress`**, defined in its own IIFE. It measures off `.about-pin-space`'s top edge, because sticky does not move an element in flow - the spacer keeps travelling at scroll speed while the composition looks frozen, which is the only ruler still moving. `.live()` reports whether the spacer has any height, so the script never restates the media queries the CSS owns. **The fill IIFE reads it off `window` per tick rather than capturing it**, because that IIFE runs *before* the one defining it - captured once, it would be `undefined` forever and the fill would silently keep freezing.
     - The sticky offset is cached and refreshed on resize, not read per scroll event: `getComputedStyle` in a scroll handler forces style resolution on every tick. **It is also re-measured once on the first scroll**, because `--nav-h` is set by the nav script further down the file - at IIFE time the sticky top still resolves to its 75px fallback, which was only correct while the nav happened to be 75px tall (found in the 2 Sep 2026 review).

   - **Scrolling drives the list, so it runs 01 to 05 on its own** and has finished before Services arrives. The band is measured from `.value-list`'s own box - it starts as the list reaches 82% of the viewport and ends with the list's *bottom* at 55% - which is what makes the short desktop row and the much taller phone column both complete inside the section. Ending on the bottom rather than the top is load-bearing: mapped off the top, 05 on a phone would only land once Services already filled the screen. Each value's turn then comes as it rises through the lower half (measured: every item opens while its own top sits between 82% and 60%).
     - **The `!!` in `setOpen` is load-bearing.** `classList.toggle(name, force)` with an *undefined* force flips the class instead of removing it. The keep expression is undefined for items beyond `n` whenever `keep` is not passed, so for a day every scroll event flipped 03/04/05 on and off - "revealing out of order" on a phone, 77 non-prefix states in a scroll-up sweep. Coerce to a boolean; verify with a fine scroll sweep that the revealed set is always a prefix.

**The About figure** (`.geo-figure`) is a **dot lattice** in which the DigiBlu **db is rendered by dot size alone** - a halftone. Generated by `scratchpad/geo/dots.cjs`. 900 circles on one exact 30x30 pitch; 78 of them carry the mark.

- **Why it is dots and no longer dashes.** The dash version carried the mark in each dash's ANGLE, turning to follow the local contour of a letterform. That is inherently ragged - the strokes are curved, the grid is not, and a curve approximated by grid-aligned ticks reads as noise well before it reads as a letter. It was reported as "messy" and no amount of blur or threshold tuning would have fixed it: the representation was wrong, not the parameters. On a lattice where every dot is the same shape on the same pitch and **only the radius varies**, there is no angle for anything to disagree about, so it cannot look untidy. Keep that property in mind before adding any per-dot rotation or jitter.
- **Radius comes from supersampled coverage, not a point sample.** Each cell asks what fraction of its own area the letterform covers, so an edge dot is genuinely part-sized rather than snapping between full and nothing. That is what keeps the outline smooth at this pitch; a single sample per cell produces a visibly stepped edge.
- **The mark pulses less than the field** (`geo-pulse-mark` at 0.95-1.06 against `geo-pulse` at 0.82-1.14) and sits at full ink against the field's 0.34. At the field's amplitude the mark's edge visibly crawls.
- **The mark phases into brand blue with the scroll**, rather than switching at a threshold. `--mark-lit` is a 0..1 value the geo IIFE writes from the figure's position in the viewport - fully blue with it centred, easing back to ink as it leaves - and the CSS mixes the fill with `color-mix`. It runs on every device: scrolling is the trigger everywhere, and hovering (where there is a pointer) forces it to full.
  - **Both go through the same inline variable**, not one as a CSS rule. An inline style outranks a stylesheet rule, so a `:hover` selector setting `--mark-lit` would never have won against the scroll handler writing it inline.
  - **`color-mix` sits behind `@supports`**, with a plain `fill: var(--text)` outside it, so a browser without it gets a legible mark in full ink rather than no fill at all.
  - **The value is quantised to 0.02 and written only on change, and `fill` transitions on hover only** (`.is-hovering`, kept for a beat after leaving so the way out fades too). Before, every pixel of scroll wrote a fresh value and restarted a fill interpolation on all 78 mark dots - paint work for a change no one could see. Fifty steps across the fade is far below what the eye resolves in a colour mix.
- **The pulse is paused while scrolling and while the figure is off-screen** (`.is-scrolling`, cleared 160ms after the last scroll event; `.is-offscreen`, from an IntersectionObserver with an 80px margin). This is the scroll-smoothness fix that matters: Chromium does not composite transforms on individual SVG elements, so 900 circles animating `scale` is a full software repaint of the figure on every frame, sitting inside a sticky composition that is itself moving. A Surface Pro X stuttered through About; a desktop absorbed it. **The six scroll handlers were measured first and cost 0.22ms per event**, which is what ruled out scripting and pointed at paint. A 6s breath at 14% frozen during a scroll is invisible; the per-frame repaint was not.

An earlier version scaled to only 1.75x with no displacement and was reported as having lost the life the dashes had: on 1px dots, scale alone reads as almost nothing.
  - **Displacement is uniform; only scale differs.** Every dot, mark included, is pushed the same 9 units, so the lattice parts as one surface. The mark moved only 2 units for a while and the figure read as a layer of dots over a logo that ignored the cursor (reported 3 Sep 2026). Scale stays split because a mark dot is `r=3.15` against the field's `1.05`: at the field's 3.4x it would be 21 units across on a 12.28-unit pitch and the letterforms would blob together under the pointer. 1.9x lands at 11.97, just inside the pitch. **Re-derive it if `R_MARK` or the pitch in `dots.cjs` changes.**

Written to the `transform` property while the idle pulse animates `scale`, so the two compose; sharing one property would silently do nothing, since a running animation beats an inline style. The falloff is smoothstepped, or the edge of the radius shows as a circular seam.

## SEO

**`SITE_ORIGIN` drives every canonical, `og:image`, JSON-LD self-URL, sitemap entry and `robots.txt` line, and it is environment-overridable** - see "Two remotes, two branches". Point it at a host that is not serving the files and crawlers are told a site you do not control is canonical, and no share card resolves.

**Per-engagement share cards**: each case study has its own 1200x630 card (`assets/og/case-studies/<key>.jpg`); blog and legal pages fall back to the site-wide `og-image.jpg`. `pageHead()` takes optional `ogImage`/`ogImageAlt`, and the alt text follows the image so a card naming one case study is never announced on another page.

**Favicon** is the real DigiBlu mark (`assets/favicon.png`), emitted as both `icon` and `apple-touch-icon`.

An SEO audit was run and its findings prioritised into a to-do list before any of it was actioned (the user explicitly asked for research first, action second). Two items have been done; the rest are tracked in Known follow-ups below.

- **Biggest lever, deliberately not touched: the single-URL architecture.** Every blog post, case study, and legal page only exists as a JS-populated modal, not a separate crawlable URL, and the content only renders into the DOM on click rather than being present on load — both cap how well any of it can be individually indexed or ranked. Fixing this properly means giving each piece its own pre-rendered page, which cuts against this project's "no build tooling, no framework" identity (see the top of this file) — a real architectural decision, not a quick edit, so it's flagged rather than done unilaterally.
- **`Organization` JSON-LD**  (`<head>`). The `FAQPage` block was removed with the FAQ section - leaving schema describing content no longer on the page would have been invalid structured data. The `@graph` wrapper was flattened to the single remaining node. `Organization` carries name, legal name, URL, `logo`, `image`, description, the real registered address (`PostalAddress`, matching the footer's `CM1 1NH` — the legal pages' `CM1 2NH` typo is a pre-existing discrepancy in DigiBlu's own published text, not something to "fix" here), and `sameAs` → the LinkedIn page.png` and `assets/og-image.jpg` are both `<head>`-only, so they have zero effect on the published artifact.** The rebuild script strips `<head>` entirely (Artifacts supply their own), so nothing in this SEO pass is visible on the claude.ai preview — it only matters once/if this ships to the real `digiblu.com`. Don't be surprised the artifact looks unchanged after this work; that's expected, not a bug.
  - Both images were generated via canvas in the browser preview, then decoded straight from the raw tool-result payload with Node (`Buffer.from(base64, 'base64')`) rather than hand-relayed through a written response — for `og-image.jpg` specifically, the base64 payload was long enough to overflow into a saved tool-result file, which turned out to be the safer path anyway (byte-exact, no transcription risk). Verify any future asset generated this way by checking the file's real signature and pixel dimensions (PNG: bytes 16–23 big-endian; JPEG: walk `0xFFC0`–`0xFFC3` SOF markers) before trusting it — don't assume a `toDataURL()` round-trip succeeded just because the tool call didn't error.
- **`og:image`/`twitter:image` now point at a purpose-built 1200×630 card** instead of reusing `hero.jpg` at whatever crop the browser happened to produce. Built from the real hero art (cover-cropped to the OG aspect ratio, not a new background), the same left-to-right scrim gradient the live `.hero` section uses, and the real DM Sans font loaded via `FontFace` before drawing — not a generic canvas fallback font. Added `og:image:width`/`height`/`type` and the previously-missing `twitter:title`/`description`/`image` (only `twitter:card` existed before).

## Environment note

Browser-preview screenshot tooling has been unreliable across sessions (`the page is not compositing frames` / stuck mid-CSS-transition reads / hangs on `img.decode()` for lazy images while the pane is hidden).

**Read this before trusting a `getComputedStyle` result on any animated property.** Because the pane often isn't compositing, `requestAnimationFrame` never fires, so **CSS transitions freeze at t=0 and never advance**. `getComputedStyle` then returns the *start* of the transition, not the target — which reads exactly like a broken style rule. This cost real debugging time twice (the G-Cloud `filter` invert and the blog filter pill background both looked broken and were not). When checking a property that has a `transition` on it, set `el.style.transition = 'none'` and force a reflow first, then read. Waiting with `setTimeout` does **not** help — a frozen transition never completes. `file://` navigation also renders as a non-interactive static snapshot in this tool — use the `.claude/launch.json` dev-server config (`npx http-server` on port 4173) instead, so the Browser preview tool loads over real `http://`. Verification has leaned on `getComputedStyle`, `getBoundingClientRect`, canvas pixel-sampling for contrast, direct `fetch()`/network checks for asset loading, `querySelector`/`click()` simulation for interactive flows, and direct cascade/rule inspection instead of visual screenshots. If screenshot tooling is healthy in a future session, a straightforward visual pass is still worth doing — everything here was checked numerically, not eyeballed.
