## Consent and analytics (9 Sep 2026)

A consent-management foundation built to be lifted onto other sites: **vanilla-cookieconsent 3.1.0** (MIT, no dependencies, ~8KB, accessible dialogs with focus trap, Escape and ARIA) driven by one configuration file, with Google Consent Mode v2 and a GA4 loader that does nothing until analytics is allowed. UK-facing, so the model is opt-in: nothing optional runs before a choice, and rejecting changes nothing about how the site works.

- **Audit first (what the Next.js site actually does in production)**: no cookies of its own; one item of local storage, `digiblu-theme`, written only when the theme button is used; no third-party requests before 11 Sep 2026, and since then exactly one, Cloudflare's Turnstile script and iframe, loaded only when the contact form's last step opens, strictly necessary, no cookies on our origin (DM Sans is self-hosted; the old `index.html` still pulls it from Google Fonts, which is why the old site is not this audit); no embeds, pixels, iframes or external scripts; one form, the contact form, which stores nothing and does not yet submit; navigation is in-page anchors plus full loads of the standalone pages, so a page view is a page load and there is no client-side routing to count. Cloudflare may add its own cookies once the site is on Workers - check after deploy.
- **Files**: `lib/consent/config.ts` (the only site-specific file: site name, measurement id from `NEXT_PUBLIC_GA_MEASUREMENT_ID`, enabled categories, storage mechanism and key, revision, policy links, the necessary-storage disclosure, page-view mode), `lib/consent/gtag.ts` (Consent Mode defaults as a string for the head, signals mapping, the GA4 loader, `trackPageView`, `trackEvent`), `lib/consent/consent.ts` (the library configured from config; `initConsent`, `openConsentPreferences`, `withdrawConsent`, `getConsentState`, `onConsentChange`), `components/consent/Consent.tsx` (mounts once in the root layout; counts client-route page views only when configured), `components/consent/consent.css` (the library's custom properties mapped to the site's tokens, so both dialogs follow the dark/light toggle), `components/consent/CookieSettingsLink.tsx` (the footer's way back in), `.env.example`.
- **Order of operations**: the first script in `<head>` is `CONSENT_DEFAULT_SCRIPT`: it creates `dataLayer`, a queuing `gtag()`, and sets every Consent Mode signal to denied except `security_storage`. Nothing Google can run before it. On mount the library reads any stored decision; `onConsent`/`onChange` call `applyConsentToGoogle`, which sends `consent update` and, if analytics is allowed, injects `gtag/js` once with `send_page_view: false` and sends one `page_view` itself. Reject means the script is never injected: no cookies, no hits, not even cookieless pings. Withdrawal mid-session sets `window['ga-disable-<id>']` (GA's own kill switch, since a loaded script cannot be unloaded), sends the denied signals, and the library's `autoClear` deletes `_ga*`, `_gid*`, `_gat*`. Re-accepting clears the switch and sends a fresh page view; the script is not injected twice.
- **Page views on a single page**: hash changes never count (`usePathname` does not change on a hash). `pageViews: "page-load"` is the setting for this site; `"client-route"` adds one per next/link navigation for a site that has any, without duplicating the loader's first view.
- **Consent record**: local storage, key `digiblu_consent`, JSON with the accepted categories, the revision, a random consent id and timestamps; 182 days; no cookie is set by the consent system at all. Bump `revision` when categories change and the banner asks again. Clearing the key brings the banner back.
- **Categories**: Necessary (read-only, lists the two local-storage items in the dialog), Analytics (offered only when a measurement id is configured, so a category is never shown empty), Marketing (in config, off; adding a marketing service means enabling it and mapping it to the three ad signals, which `consentSignals` already does).
- **Design**: equal-weight Accept all / Reject optional / Manage preferences, no pre-ticked boxes, no dark patterns; the page stays interactive behind the banner (`disablePageInteraction: false`); bottom-left box on desktop clear of the scroll-to-top disc, full width on a phone; the dialogs take the site's font, radii, brand-sweep primary buttons and theme tokens. **The category blocks in the preferences dialog take a 10px radius of their own (10 Sep 2026)**: the library styles them with the button radius, and with the site's pill buttons (999px) an expanded block went pill-shaped and its overflow-hidden description wrapper clipped the description, the table caption and the first and last table columns at the curved corners (reported with a screenshot); `consent.css` overrides the block, title and description-wrapper radii, and the buttons keep the pill.
- **Verified** (dev server, both viewports): new visitor sees the banner with the default signals already denied and no Google request; Reject stores a necessary-only record and loads nothing; the choice survives reload; Cookie settings reopens the dialog without a reload; allowing analytics injects `gtag/js`, sends granted signals, `config` with `send_page_view: false` and exactly one `page_view`; anchor navigation adds none; reload with analytics allowed loads GA and sends one view; withdrawing flips the kill switch and the signals; re-accepting sends one more view with one script tag; clearing storage brings the banner back; console clean. The gtag request itself cannot be observed here (the pane has no outbound network) - Realtime and Tag Assistant confirm it in production.
- **The real property is connected since 10 Sep 2026**: GA4 property "DigiBlu website", web stream "digiblu.com", measurement id **G-RVNLDVSLJ8**, created by DigiBlu following the step-by-step in the session (account data sharing off except support, GDPR data processing terms accepted, enhanced measurement on with site search and form interactions off, a second administrator added). **The id comes from the environment only - `lib/consent/config.ts` has no fallback any more** (it was the `G-XXXXXXXXXX` placeholder, which would have loaded a bogus tag on any build that forgot the variable): production sets `NEXT_PUBLIC_GA_MEASUREMENT_ID` in Cloudflare's build variables, `.env.local` (gitignored) carries it for local testing, `.env.example` documents it, and `next.config.ts` prints a warning at build time when a production build (not `noindex`) has no id, so the live site cannot ship without analytics unnoticed. **Retested against the real id on the dev server the same day**: fresh visit shows the banner with every signal denied and no Google script; Reject stores necessary only and loads nothing; Accept all injects `gtag/js?id=G-RVNLDVSLJ8`, sends `consent update` with `analytics_storage` granted, `config` with `send_page_view: false` and exactly one `page_view`, and Google's `_ga` and `_ga_RVNLDVSLJ8` cookies appear (so the tag ran, and the cookie table names the real cookie); Reject from Cookie settings flips `ga-disable-G-RVNLDVSLJ8` to true, sends the denied signals and clears both cookies. Those test hits reached the property from localhost, which is what the internal-traffic filter in GA4 Admin is for once DigiBlu's addresses are known.
- **Not done, deliberately**: no marketing pixels, no Google Ads, no server-side tagging.
- **The policy is the "Privacy and Cookies Policy" since 10 Sep 2026, and its sections 12 and 13 are ours, not DigiBlu's published text** (drafted on request, **approved by DigiBlu on 10 Sep 2026**; every other section of every legal document stays verbatim from digiblu.com, except the three Terms edits noted at the end of this bullet). Section 12, "Cookies and Similar Storage", says exactly what the site does: the two local-storage items (`digiblu_consent`, six months; `digiblu-theme`, until cleared), Google Analytics 4 only with permission and the two cookies it sets (`_ga`, `_ga_RVNLDVSLJ8`, up to two years), nothing loading until a choice is made, withdrawal from Cookie settings, no advertising or marketing cookies, no chat, surveys or sign-in. Section 13 replaces the old server-log claims with what actually happens on Cloudflare (IP and device details processed to deliver and protect the site, aggregate logs for troubleshooting, no profiling). The published section 12 described cookies the site does not use (sign-in, surveys, live chat). **The slug and URL stay `privacy-policy`**: the redirect map, the consent config, the footer and the contact form's consent line all point at it, and only the visible name changed (footer link, consent banner link, the contact form's checkbox label, the page title). **Keep section 12 true**: adding a cookie, a category or a service means editing it and the consent config together. The contact dialog's consent line also carried the old site's `legal/privacy-policy.html` href, a 404 on this site for a ctrl-click; it is `/legal/privacy-policy` now. **Sections 12 and 13 use plain lower-case you, we and our** (10 Sep 2026, asked for with the approval: "fix the capital letters in the middle of phrases"); the published sections keep the template's capitalised You/We/Our, which the Terms define as terms in their section 1 and the privacy policy never defines - lowering the rest of the policy is a one-line change if DigiBlu asks. **No separate Cookie Policy will be published** (decided the same day; the combined document is what the footer links). **The Terms of Use were read for platform assumptions the same day**, on request: nothing in them assumes Wix, and three edits were made - the introduction and section 15 named "Our Privacy Policy" and a separate "Our Cookie Policy" and now name the Privacy and Cookies Policy; section 2 gave the registered office postcode as CM1 2NH, which Companies House (company 12015792, checked 10 Sep 2026) gives as CM1 1NH, the footer's value, so it is corrected; and the intro date moved to 10 September 2026. The privacy policy and the carbon plan already said CM1 1NH.

## Pages over dialogs and the contact API (11 Sep 2026)

> **Superseded on the `pages-only` branch (18 Sep 2026):** Radu asked that content be available only through its pages. The service, case-study reader, accreditation, team-profile and legal dialogs are removed with their behaviours, markup, data hooks, `lib/client/modal.js` and about 10KB of CSS that only they matched (checked selector by selector against every source file; the rules the pages share kept their `.service-modal-*` / `.case-modal-*` names). Every opener was already a real link, so each now simply navigates. The contact form stays a dialog as well as `/contact`, proposed to Radu as a form rather than content; its privacy-policy link already opened in a new tab. The team strip keeps its desktop card and bio; opening a profile goes to `/team#<key>` (a button calling `location.assign`, since the slices are buttons that also expand; the footer's Our Experts link is the crawl path). The home page went from 371KB to 271KB of HTML (next build); most of the rest is Next's own RSC payload repeating the page's markup, the About figure's 987 circles above all, not content. `pages.test.cjs` asserts one overlay on the home page and that no legal, service, accreditation or case-study text is in it; against the old build it found all 28 documents. Verified in `digiblu-vinext` at 1672px and 375px: every opener navigates with its default untouched, the contact dialog opens and closes with no `inert` left, team slices reach `/team#<key>`, no horizontal overflow, no failed requests. The text below describes the dialogs as they were.
>
> **The contact form followed the same day**, on DigiBlu's side of the discussion: one way in, and simpler code. `ContactDialog.tsx` is gone; the hero's nav button and CTA and the footer's Contact Us are plain links to `/contact`; `ContactForm.jsx` lost its overlay-only code (openers, close, backdrop, Escape, focus trap, inert, the `/#contact` arrival) and `ContactFormBody` its heading prop (always the page's h1); the `.modal-overlay`, `.modal-close` and `#contactModal` rules went. The mobile menu now closes on any link click (`closest('a')`), which the Get in touch link needed once it stopped carrying `.js-contact-open`. Home page HTML 271KB to 260KB. **Enquiries are measured**: a successful send calls `trackEvent('generate_lead', { lead_source: 'contact_form' })`, GA4's recommended lead event, dropped unless analytics consent stands and never carrying a field; section 12 of the policy says so ("how many send an enquiry ... never what you wrote"), pinned by `content.test.cjs`. Verified in `digiblu-vinext` with the API stubbed (no email sent): with analytics allowed, one event with only `lead_source`; with it rejected, none and no Google script; a failed send shows the API's message and records nothing; Done returns an empty step 1 with focus on the first field. DigiBlu has to mark `generate_lead` as a key event in GA4 Admin for it to show as a conversion. Analytics is opt-in, so the count is a floor; the mailbox is the total.

DigiBlu's developer reviewed the site before its planned Monday deployment and returned four points: (1) "for all intents and purposes a single page app, everything in a modal, modals are not crawlable, separate pages please"; (2) page metadata and social cards correct on every page; (3) the contact form needs a backend endpoint (they add the downstream call), Cloudflare Turnstile, and keys in environment variables; (4) the Safari Destinations placeholders (acknowledged by DigiBlu, left). **What was true**: case studies and legal documents already had pages, but the services write-ups, the team bios, the accreditation descriptions and the contact form existed only inside dialogs that script fills after load, so the home page's crawlable text was about 6,000 characters; and `SITE_ORIGIN` defaulted to the retired GitHub Pages host, so any build without the variable carried a dead address in fourteen places of its metadata, which is what the reviewer saw.

**Option A, chosen by DigiBlu: pages under the dialogs, nothing visibly changed.** Four listing pages - `/services` (every service in full, numbered in card order, an anchor per key, a "Discuss this service" CTA to `/#contact`), `/team` (the eight bios, `Person` JSON-LD), `/accreditations` (the six marks and descriptions), `/case-studies` (the index of ten, the reader's row style as real links) - each with its own title, description, canonical, share card (`public/assets/og/<name>.jpg`, 1200x630, built from the hero art like the case-study cards) and JSON-LD `ItemList`, sharing `components/PageIntro.tsx` and the `.detail-page` frame (`.page-list` / `.page-item` in `globals.css`, with `scroll-margin-top` off `--nav-h` so an anchored item clears the fixed nav). **Every home-page opener is a real link** - `<a href="/services#ai" class="service-learn-more">`, the accreditation chips to `/accreditations#key` (both groups), View all to `/case-studies`, the footer's service links to `/services#key` on every page, an Our Experts footer link (the team strip's slices are buttons and stay so; a "Read the full profiles" link under the strip was added and removed the same day as redundant, the footer link being the crawl path) - **and the dialogs stay as progressive enhancement**: each behaviour opens on a plain click with `preventDefault()` and returns early on a modified click (meta, ctrl, shift, alt, middle button), the pattern the case-study cards had since the reader. Verified by dispatching plain and ctrl clicks on each opener: plain opens the right dialog with the default prevented, ctrl leaves the default alone, no `inert` left behind. **The contact form is both a dialog and a page since the same afternoon** (`/contact`, approved by DigiBlu): `components/ContactFormBody.tsx` is the one markup, rendered inside the dialog's overlay on the home page and inside a `.modal-panel.contact-panel` in the flow on the page (where the aside title is the page's h1; `.modal-aside h1` shares the h2 rule); `ContactForm.jsx` takes `rootId` and gates the overlay-only parts (openers, close, backdrop, Escape, focus trap, inert) on `isDialog`, so the steps, validation, phone filter, Turnstile and submit are one code path, and Done closes the dialog or brings the page's empty form back. Every contact opener is `<a href="/contact" class="js-contact-open">` (the hero's nav button and CTA, the footer's Contact Us, the service dialog's CTA), opening the dialog on a plain click and navigating on a modified one; the standalone pages' Get in touch and Contact Us, and the services page's CTA, go straight to `/contact`; `/#contact` still opens the dialog on arrival for old links, and the redirect map's `/contact-us` goes to `/contact`. **The standalone pages' nav (`PageHeader.tsx`) goes to `/services`, `/case-studies` and `/team`** rather than back to the home page's sections; the home page's own nav still scrolls. `robots.txt` disallows `/api/`. Services' content `order` matches the card order now (discovery 2, process 3), so the page numbers agree with the cards; team entries carry a `key` (the file name) for the anchors. The sitemap lists twenty-one URLs. The service dialog's never-reached numbering fallback referenced the old script's `SERVICES` object, which does not exist in the port; it reads the `services` prop now. The redirect map sends the old service pages to `/services#key`, the leadership addresses to `/team` and the project addresses to `/case-studies`; the old `/case-studies` row was dropped because the new site answers at that address and the row would have looped.

**Metadata.** `SITE_ORIGIN` defaults to `https://digiblu.com`. `scripts/pages.test.cjs` (`npm run test:pages`, after `npm run build`; CI runs it after the build step) reads every prerendered page and asserts a unique title, a 50 to 160 character description, a canonical on the origin (the home page's has no trailing slash, Next's doing), an `og:image` on the origin whose file exists under `public/`, `og:title` equal to the title, a Twitter card, JSON-LD and no trace of the retired host; that the listing pages carry the dialogs' content; that the home page links to every listing page; and that the sitemap lists every page. Its first run found the legal pages shipping with no share image at all - **a page's `openGraph` object replaces the layout's rather than merging with it, so every page must name its images** - and four descriptions over 160 characters, all fixed.

**Contact API.** `POST /api/contact` (`app/api/contact/route.ts`, the only dynamic route; the Worker runs it and the static pages are untouched) takes JSON `{ firstName, lastName, email, phone?, company?, message?, consent: true, website: "", turnstileToken }`, validates it (`lib/contact/validate.ts`: trims, caps lengths, requires both names, a plausible email and `consent: true`, rejects a filled honeypot), verifies the token with Cloudflare (`lib/contact/turnstile.ts`, `TURNSTILE_SECRET_KEY` from the environment, `cf-connecting-ip` passed along) and calls `sendEnquiry()` in `lib/contact/send.ts` - **the one function the developer replaces** with the Azure Communication Services call; today it logs that an enquiry arrived, with no personal data. Answers: 200 `{ok:true}`; 400 on validation with the message the form shows; 403 when the token is missing or fails; 500 when no secret is configured or the send throws. The form (`ContactForm.jsx`, hand edits noted in the file) loads Turnstile's script the first time step 2 shows and renders the widget explicitly in `#cf-turnstile` (`NEXT_PUBLIC_TURNSTILE_SITE_KEY` passed as a prop from `HomeBehaviours`, theme from `data-theme`), carries an off-screen honeypot (`#cf-website` in `.cf-hp`, not `display:none` so scripts still fill it) and an error line (`#cf-error`, the `--error` token, 8.1:1 dark and 6.1:1 light), posts with `fetch`, shows the success screen only on 200, and otherwise shows the API's message and resets the widget. The CSP admits `https://challenges.cloudflare.com` in `script-src` and `frame-src` (it was `frame-src 'none'`). **Keys**: the site key is a public build variable, the secret a Worker secret (`wrangler secret put TURNSTILE_SECRET_KEY`), neither in the source; `.env.example` and `.env.local` carry Cloudflare's documented test pair, which always passes; `next.config.ts` warns on a production build without the site key, as it does for the GA id. The modules use relative imports with explicit `.ts` extensions (`allowImportingTsExtensions` in tsconfig) and web-standard `Request`/`Response`, so `scripts/contact.test.cjs` loads them directly under node:test with the verify call mocked. Verified end to end on the dev server: the widget passes with the test key, a submit posts 200 and shows the success screen with focus on Done, a filled honeypot posts 400 and shows the error line, no cookie appears on our origin, the dev log shows the receipt line. **Turnstile and the policy**: Cloudflare's Turnstile privacy notice calls the signals it collects strictly necessary for bot detection, and the only cookie it can issue, `cf_clearance`, comes from the pre-clearance feature, which is off; section 12 of the Privacy and Cookies Policy says so in a paragraph added the same day (awaiting DigiBlu's nod, as sections 12 and 13 were), and the policy date moved to 11 September 2026.

**Microsoft named as the enquiries processor (18 Sep 2026).** Once the contact form went live through Azure Communication Services (Radu, 14 Sep 2026), the same paragraph's closing sentence, "The details you enter are passed to us", no longer said who carries them; section 14 (DigiBlu's text) promises personal data goes to third parties only "as set out in this notice", so naming the processor is what keeps that true. The sentence now says the details are sent to DigiBlu by email through Azure Communication Services, an email service provided by Microsoft, which processes them on DigiBlu's behalf; that Microsoft describes its handling at privacy.microsoft.com (plain text, like every other address in the policy, and asserted by the test); and that the details are used to respond and for nothing else. The date moved to 18 September 2026.
